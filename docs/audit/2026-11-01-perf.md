# Live-simulation performance audit (phase P0, 2026-11-01)

Scope: audit only. No sim, session, wire, engine or API code changed on branch `perf` (base `88483d2`, upstream unset). New code is analysis layer only: `cubesat/perf_bench.py` + `cubesat/perf_ws.py` (`--mode perf`), `cubesat/perf_gc.py` (GC probe), tests in `tests/v2/test_perf_bench.py`. Every number below comes from a committed JSON; "unmeasured" means no JSON holds it.

Commands (both from the repo root of the worktree):

```
uv run python -m cubesat.benchmark --mode perf --base data/scenarios --report data/eval/perf_baseline.json --repeats 3
uv run python -m cubesat.perf_gc --base data/scenarios --scenario live_24sat --report data/eval/perf_gc_probe.json --repeats 3
```

## 1. Measurement quality (read this before trusting a digit)

- Machine: Apple M3, 8 cores, macOS-26.1-arm64-arm-64bit, Python 3.12.4, numpy 2.5.4, scipy 1.18.1. Shared with other agent sessions all day.
- `perf_baseline.json`: load average (1, 5, 15 min) at start (1.83, 8.12, 9.66), at end (1.94, 2.62, 5.14); `machine_busy` = **false** (rule: load1 > 2.0 or a pytest process at start; neither held). The run started after a 12-minute wait for quiet, but the 5- and 15-minute loads at the start (8.1, 9.7) show the machine had been heavily loaded minutes earlier, and load1 1.83 is only just under the threshold. Treat it as "mostly quiet", not "idle".
- Noise: every timing is 3 repeats, median kept with min-max. Across the 92 timing sets the median (max-min)/median is 3.7 %; the worst are 15.4 % (proximity_stress compute_s), 10.5 % (proximity_stress inject50), 8.4 % (live_2sat first_frame_s) (the first is a 0.08 s run, so an absolute spread of a few ms).
- `perf_gc_probe.json` was taken right afterwards while another session was back on the machine (load1 3.25 at start, 3.80 at end): **measured under load**. Its absolute seconds are not comparable to `perf_baseline.json` (total 11.0 s there vs 9.4 s compute in the baseline); only the gc_on / gc_off contrast inside the same file is meaningful.
- Earlier numbers quoted in the brief and the master map (two_failure 1.77 s, live_12sat 4.90 s, live_16sat 7.87 s, live_24sat 14.96 s) were measured under load ~3-4 and are about 1.5-1.7x the quiet-machine values here. Do not mix them.
- What the harness does and does not do is spelled out in the JSON's `notes`. The two non-obvious points: tick timing uses a `cancel_event` stand-in that stamps once per tick (the log is byte-identical with it, pinned by `test_timing_instrumentation_never_changes_a_log`), and the inject latency parks the playback cursor by setting `Session._cursor` / `_last_frame_t` (private fields) while the driver idles, then calls the real `Session.inject_failure`.
- Not measured at all: browser render time, GIL contention between a compute worker thread and the event loop, snapshot()/restore() cost, memory (the wire JSON of one whole 24-sat v1 run is 44.4 MB, `wire.bytes_total` in the JSON; resident size of the retained log unmeasured).

Derived from the two tables (arithmetic on the committed medians):

- First frame / compute = 0.97-1.04 for all 19 rows: the live path pays the whole run before frame 0.
- Inject / compute = 0.91-1.08 at every cut point (25/50/75 %) except `proximity_stress`, a 0.08 s run: inject cost does not depend on when the failure lands.
- Scaling with swarm size, compute 6 -> 24 sats: exponent 1.46 (ln(9.36/1.24)/ln 4); 12 -> 24 sats 1.59. Not n^2.
- Compute-only tick rate (1 / mean tick): 8,154 / 910 / 2,646 / 1,454 ticks/s (two_failure v1, live_24sat v1, two_failure v2, live_24sat v2). Playback at speed S with dt 2 s needs S/2 ticks/s.

## 6. Where the measurements contradict the brief

1. "~n^2": measured exponent 1.46 (6 -> 24 sats), 1.59 (12 -> 24). The pairwise loops are O(n^2) in calls but about half the time, and everything else is linear in n.
2. "Known facts" (1.77 / 4.90 / 7.87 / 14.96 s): 1.05 / 3.12 / 4.81 / 9.36 s on a mostly quiet machine. The earlier numbers were load artefacts; the shape (whole-run precompute, compute-bound inject) is confirmed.
3. "Wire build adds 0.2-0.9 s": per run that is true (0.22 s two_failure, 0.76 s live_24sat for to_messages + encode, two_failure 0.224, live_24sat 0.756, live_24sat@v2 1.001), but it is spread over playback frame by frame, not before the first frame, and it is 7-23 us (to_messages) + 19-66 us (encode) per frame.
4. "Inject holds playback and recomputes": confirmed, and on `live_24sat` it does not even finish (F3). The brief expected a latency; there is none, only a 500.
5. "30 Hz emit cap": the cap is not the whole story; at speed 60 jitter makes it 19.5 frames/s (F10).
6. Map F3 / audit A-17: "charts re-render from full growing arrays on every WS frame (30 Hz)". By code reading only one chart does (DvChart, section 8): the shared history store samples at 2 Hz, so the other four charts re-render at 2 Hz. Render cost in the browser is unmeasured.
7. The expectation that `tick_ms_max` marks replanning: on no-failure runs it is GC (F6).
8. Master map E1 quotes 4.6 / 11.6 / 32.2 s at 6 / 12 / 24 sats; this baseline has 1.27 / 3.11 / 9.32 s. Same conclusion as audit 2026-10-31 section 5.1.

## 9. Does P1's design match the measurements?

Plan step 4 / map L1: a worker thread steps the engine a bounded number of ticks ahead of playback, inject = `engine.inject()` at the playback tick plus discarding buffered ticks, seek = nearest snapshot.

Matches:
- Compute-bound whole-run precompute is the dominant latency (F1/F2): first frame and inject are 1.0x the full compute, independent of when the failure lands. A stepper removes both in principle: engine setup is 0.2-0.6 ms (`setup_s`), a tick is 0.03-1.1 ms.
- The worker has enormous headroom against playback: 910 ticks/s (v1) and 1,454 ticks/s (v2) at 24 sats, mean, against 50 ticks/s needed at 100x and 500 at 1000x. The map's target of >= 100 ticks/s at 24 sats is met 9-14x on compute alone.
- A lookahead of about 10 s of playback is not needed to hide replan spikes (40-100 ms ticks): 10-20 ticks of buffer cover them.

Needs a change or a check:
1. **v1 has no stepper.** All 17 committed scenarios are v1. A streaming session on `EngineV2` helps only v2 scenarios, and `EngineV2` has no recovery (no replan) yet, so the demo that matters (failure, replan, reseat) cannot stream until either Phase 5c's recovery lands in v2 or v1 gets the SimEngine extraction the map asks for. Until then the 1-9 s first frame and compute-bound inject stay on every shipped scenario.
2. **F3 is not a streaming problem.** Streaming does not make an infeasible replan feasible; `live_24sat` + one failure needs an allocator decision first.
3. **GC (F6) argues for streaming frames out instead of retaining them**; a worker that also appends to a list will keep the 50-100 ms pauses (and the pause lands on the worker, which holds the GIL).
4. **GIL**: the v1 loop is Python-bound (F4). A worker *thread* will contend with the event loop and the websocket writes. Unmeasured; P1 should measure frame-time jitter with a worker thread before committing to threads over a process.
5. **Snapshot cost is unmeasured and `EngineV2.snapshot()` serialises the whole `cov` list (grows with k)**; measure at k = 8,515, 24 sats before sizing the snapshot cadence.
6. **The emit cap (F10) and the driver loop (F12) are session code that P1 rewrites anyway**; fix the cadence rule there (stride by sim time) rather than patching the wall-interval test.
7. Quick wins that need no redesign: F9 (encode once per message), F4 for v2-only paths, F5. F4 on v1 is only allowed if every committed v1 log stays `cmp`-identical.
