Servers were run from wt-audit on 127.0.0.1:8101/8102/8103 and all were killed. wt-audit `git status` is clean (my 19 uploaded scenario files were deleted). Architecture fact that frames everything: the app has ONE process-global `Session` (api.py:57 `get_state`). "Three concurrent sessions" are really three clients driving one shared session. Isolation between sessions does not exist, so I tested (a) three HTTP+WS clients on one server and (b) three `Session` objects in one Python process (which is what the L1/L2 session rewrite would create).

Severity as in the map: P0 demo-breaking or invalidates a claim, P1 wrong result, P2 quality. Known map IDs are cited, not re-reported.

## Findings

### P1

**B-1 (P1) Lifecycle calls are not serialized. Concurrent starts interleave and show a stream mislabelled as another run.** session.py:247-306 (`start_live`), :380-424 (`inject_failure`). Track L1 (session rewrite), stopgap `asyncio.Lock` per Session.
`start_live` does `_teardown()`, awaits a 2-40 s thread, then unconditionally assigns `self._source`. A second start arriving during that await is not rejected, and the first one overwrites it when it finishes.
Repro: `.venv/bin/python $B/t13_three.py` (3 clients start live_24sat/even_split, live_12sat/hungarian_keepout, live_6sat/hungarian at t=0, 0.5, 1 s):
```
0 ('live_24sat.json', 'even_split', 200, 40.6, 'live_6sat', ["('live_6sat', 6)"])
1 ('live_12sat.json', 'hungarian_keepout', 200, 31.3, 'live_6sat', ["('live_6sat', 6)","('live_6sat', 12)","('live_6sat', 24)"])
2 ('live_6sat.json', 'hungarian', 200, 16.8, 'live_6sat', ['live_6sat',...])
```
All three clients get 200 "started", the response and `sim_state.scenario` say `live_6sat` but the frames carry 6, then 12, then 24 satellites. In-process version (`$B/t5_race.py` A/B): `enrich.scenario=live_6sat | source scenario=live_12sat | policy hungarian_keepout`. Also, because `run_scenario` resolves `cubesat.sim.replan` at call time, the in-flight thread of start A switches policy when start B rebinds the seam, so A's output (shown to the user) is a mixed-policy run. Fix: serialize start/load/inject/reset with one lock, or tag each start with a generation counter and drop the result if the generation moved.

**B-2 (P1) A slow injection recompute can clobber a newer run, and two simultaneous injections lose one.** session.py:399-424. Track L1.
Repro (`$B/t5_race.py` cases C and D):
```
concurrent inject results: [None, None] | failures in source: [(1, 'DEAD')]       # SAT-2 and SAT-3 both returned 200, only one applied
after new start: source nominal
after stale inject returns: enrich.scenario= nominal | source= live_6sat | failures 1   # old run's recompute replaced the new run
```
Cause: `with_failure` is based on the `source` captured before the await; the result is applied without checking that `self._source` is still that source and not stale. Fix: after the await, `if self._source is not source: discard`, and apply the failure to the current scenario under the lock.

**B-3 (P1) Failure injection rewinds playback by (recompute seconds x speed).** session.py:399 (`t_now` captured before the await), :422 (`_cursor = bisect_right(new_source.times, t_now)`). Track L1 (map L1 "injection = engine.inject() at the playback tick" fixes it, but until then it is live).
The driver keeps streaming during the 2-17 s recompute, then the cursor snaps back to the pre-compute `t_now`.
Repro: `.venv/bin/python $B/t17.py` (live_6sat, speed 100, inject SAT-4 at 2 s): `backwards 100 406.0 -> 101 204.0`. The UI sees sim_time go 406 -> 204 and frames 204..406 replayed. At 24 sats (17 s) x speed 100 that is a 1,700 s rewind; at higher speeds it can restart the run. Fix: after the await, set `t_now = self._last_frame_t` again (the failure was scheduled earlier, so frames in the gap differ, so also `cancel_driver()` before the await) or pause the driver during recompute.

**B-4 (P1) Live EPS_DEGRADE injection never shows DEGRADED; the sat goes healthy -> failed.** session.py:105-120 (`with_failure` fades from `max(t_now - degrade_s, 0)`, i.e. inside the already-streamed prefix), wire.py:57 (default `degrade_s=600`). Track L1 (map §5 L1 says "fixes the EPS live-injection bug for free"; it is not in §2, this is the evidence). The `degrade_s` fade lies in the past, so the injected sat dies at t_now.
Repro: `.venv/bin/python $B/t16_inj.py`:
```
EPS_DEGRADE SAT-4 deg=None  status transitions [(0.0,'healthy'), (204.0,'failed')]
EPS_DEGRADE SAT-5 deg=100   status transitions [(0.0,'healthy'), (604.0,'failed')]
EPS_DEGRADE SAT-1 (leader)  status transitions [(0.0,'healthy'), (4.0,'failed')]
```
No `degraded` status ever appears for any of degrade_s 0/100/600. The failure also arrives in the event log at the old time with a retroactive DEGRADE_START. DEAD and THRUSTER_OUT injections work (healthy -> failed at t_inj+2 ticks, THRUSTER_OUT at t_inj) apart from B-3. Fix: schedule EPS fade as `degrade_start = t_now`, `die at t_now + degrade_s` (needs the Failure schema to separate fade start from death time).

**B-5 (P1) Abandoned compute threads are never cancelled (reset / client abort / replacement start).** session.py:286-296 (`cancel` set only in the timeout branch), :352 (`reset` -> `_teardown` never touches the event). Track L1.
Repro: `.venv/bin/python $B/t6_orphan.py $S/srv1.pid` (6 x [POST start live_24sat with 0.3 s client timeout, then POST reset]):
```
idle ['26160','0.0']
t+2s  ['55744','193.6']   t+7s ['116000','196.5']   t+22s ['157360','196.6']   t+32s ['185760','201.0']
...drain ~40 s later: ['14128','0.0']
```
Six abandoned starts keep the server at about 200% CPU for ~40 s and +160 MB RSS. Linear in the number of abandons, so a user who mashes start/reset on a 512 MB host can OOM it, and every real run is slowed by the orphans (GIL). The 504 path already cancels cooperatively, so the infrastructure exists. Fix: store the current `cancel` event on the Session; `_teardown()` and "start replaces start" set it.

**B-6 (P1, latent in HTTP today, certain under L1/L2 or any second `Session` in the process) The replan seam is process-global, so one session's policy leaks into another and the leak survives teardown.** session.py:433-453 (`_install_seam`, `_restore_seam`), docstring :437-440 claims "safe under one-Session-per-process". Track L1.
Repro: `.venv/bin/python $B/t4_seam.py`:
```
baseline default replan: replan a94da9abe5b9
after s1 even_split start, sm.replan = even_split_replan
s2 default 'hungarian' session now computes hash fab9648d14f5 ==baseline? False      # s2's "default" run silently uses s1's policy
sm.replan with s1(even_split)+s3(hk) open: hungarian_keepout_replan
after s1.reset: replan          (original)
after s3.reset: even_split_replan                                                        # s3 "restores" s1's rebind
after s2.reset: even_split_replan is original? False
default-run hash now: fab9648d14f5 baseline a94da9abe5b9                                # process permanently corrupted
```
After the interleaved teardowns every later default run in the process is not the golden run (golden determinism broken until restart). The same mechanism is what makes B-1's in-flight thread change policy mid-run. Fix: stop rebinding module state; pass `replan_fn` as an argument to `run_scenario` (sim.py already resolves it at one call site), which also removes B4's `except TypeError`.

**B-11 (P1 for a public deploy) One shared global session with no authentication; no-body POSTs are cross-site forgeable; WS has no Origin check.** api.py:57, :364-399 (routes), :412 (`/ws/state`). Track D/L1 (L1's session rewrite is the real fix).
